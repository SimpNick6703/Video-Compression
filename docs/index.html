How the PCIe numbers are calculated

One raw frame in NV12 / YUV420p takes width × height × 1.5 bytes.

  • 1080p: 1920 × 1080 × 1.5 = 3,110,400 B/frame (3.11 MB) × 14,217 = 44.22 GB (186.6 MB/s per 60 fps worker)
  • 720p: 1280 × 720 × 1.5 = 1,382,400 B/frame (1.38 MB) × 14,217 = 19.65 GB (82.9 MB/s per 60 fps worker)

Native 1080p: frames never leave VRAM. Only the compressed bitstream crosses PCIe: 457 MB in + 88 MB out ≈ 545 MB.

Downscaled to 720p (legacy hybrid): FFmpeg downloads every decoded 1080p frame to system RAM for CPU Lanczos scaling (44.22 GB device → host), then uploads the 720p frames back to NVENC (19.65 GB host → device). With the bitstream that is ≈ 64.41 GB of PCIe traffic.

Hardware Native Unscaled (1080p60)

Zero-copy VRAM execution with zero software scaling copies.

Frames are demuxed from storage and streamed as compressed NAL packets across PCIe into GPU VRAM. NVDEC decodes into CUDA surfaces, the frame scaling filter is completely bypassed (zero software pixel copies), and NVENC encodes directly on-chip. Only compressed bitstream traverses PCIe.

Why it matters: When the BPP calculator decides to downscale (for example 1080p to 720p), running the scaler on the CPU forces a ~64 GB PCIe roundtrip. The zero-copy pipeline resizes frames in video memory with each vendor's native scaler instead: scale_cuda on NVIDIA, scale_vaapi on VA-API, vpp_amf on AMD, vpp_qsv on Intel and scale_vt on macOS. The NVIDIA case measured here gets back to native 545 MB PCIe traffic without losing quality. If an input cannot be decoded in hardware, the pipeline falls back to an upload tier, then to the legacy path.

5 · Split & stitch

How one video becomes two parallel encodes

Hardware encodes run as two workers at once. The split point is found by reading packet headers only, so no video is decoded to choose it.

  1. Step 1 · Probe

    Read packet headers

    ffprobe -select_streams v:0
  -show_entries packet=pts_time,size,flags
  -of csv=p=0

    A line-by-line reader adds up packet sizes and notes keyframe timestamps (flags=K). No frames are decoded and memory stays under 10 MB.

  2. Step 2 · Balance

    Split at 50% of the bytes

    The split point T is the keyframe closest to half of the total byte weight, so both workers get an equal amount of data. Cutting on a keyframe means each half can be decoded on its own.

  3. Step 3 · Encode

    Two workers in parallel

    Worker 1 encodes 0 → T, worker 2 encodes T → end, each as its own FFmpeg process with a bitrate for its half. Worker 2 resets its timestamps to zero with -avoid_negative_ts make_zero.

  4. Step 4 · Stitch

    Join without re-encoding

    ffmpeg -f concat -safe 0 -i list.txt
  -c copy -movflags +faststart

    The concat demuxer joins both halves in under a second and moves the index (moov box) to the front of the file so it can start playing before it fully downloads.

Known issue: the stitch currently leaves a 40–100 ms gap in video timestamps at T. Playback stutters briefly there and video runs slightly behind audio for the second half. A fix is planned for the next release; see Known Issues.

Parallel Processing Engine

By dividing the video at a calculated keyframe and utilizing Python's threading to run multiple FFmpeg subprocesses simultaneously, the tool significantly reduces encoding times on modern multi-core systems and hardware encoders.

Progress Aggregation

A thread-safe ProgressTracker class parses stderr from both FFmpeg instances, merging ETA and speed metrics into a unified console output.

Parallel Split Encoding

Hardware encoders execute a dual-worker parallel split pipeline with on-chip rate control and hardware lookahead for maximum speed and bitrate compliance.

Safe Concatenation

Chunks are stitched using FFmpeg's concat demuxer with +faststart, relocating the moov atom to the front for progressive streaming without re-encoding.
